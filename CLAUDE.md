# Working conventions for this repo

- **Docs flow**: substantive notes, explanations, and caveats produced while working are persisted into `README.md` here — not left in chat. Improvement suggestions for the DSL package go into that package's own TODO tracking, not into its sources; never modify that package's code unless explicitly asked. Once a suggestion is addressed, its TODO entry is removed (no addressed-item records) — residual contract notes become small doc comments in that package's code or one-line README additions, left uncommitted for review.
- **Dependency**: this generator targets the DeclarativeRequests DSL, [swift-declarative-requests](https://github.com/sisoje/swift-declarative-requests). `Package.swift` depends on its published tags by URL. `../swift-declarative-requests` is a local sibling checkout serving one purpose only: reading DSL sources for semantics before changing codegen — never a path dependency, since that would make the package unresolvable for anyone else. Anything meant to be read outside this machine (docs, links, comments) references the GitHub URL, never the `../` path.
- **Work vs release**: `Package.swift` and CI name the published tag — no path dependencies anywhere. To develop against unreleased DSL changes, `swift package edit swift-declarative-requests --path ../swift-declarative-requests` (untracked workspace state); `unedit` and re-run `swift test` before tagging a release.
- **Golden sync**: whenever codegen output changes, regenerate `Sources/PetstoreAPI/Petstore.generated.swift` by running the generator on `Specs/petstore.yaml` — the golden test compares byte-for-byte.
- **Spec file**: `Specs/petstore.yaml` is the byte-exact canonical petstore file from the OAI repository; don't reformat it.
- **Verification**: `swift build && swift test` must be green before declaring anything done. Compiles-against-the-DSL is proven by the build itself: the checked-in `<Name>API` targets are generator output (golden test pins byte-equality) building against the real dependency.
- **Adding a spec example** (established over petstore/museum/supabase): download the canonical file byte-exact into `Specs/`, run the generator, extend the generator for real gaps the spec exposes (with unit tests), check the output into a new `Sources/<Name>API` target depending on DeclarativeRequests, add the spec to the parameterized golden test, add request-shape tests, update README. Hand-written layers over a generated enum go in the same target as a separate `<Name>Wiring.swift` — never edit the `.generated.swift` file.
- **Skill**: load `declarative-requests-spec-patterns` before writing or reviewing wiring layers / codegen output that consumes the DSL.
- **Boundary rules for codegen changes** (see README "Design conclusions" for the full list): three homes, no exceptions — spec facts in generated files (plus one-line bindings to runtime mechanics), universal mechanics in `DeclarativeOpenAPIRuntime`, app policy in wirings. Generated files carry spec facts only — a change that puts a concrete binding (`URLSession`, `JSONDecoder`), a parameter default, or hand-maintained spec knowledge into either side is wrong by construction. New generated sections must be absent when their spec input is absent. Errors are lossless structs; derived values are projections, never stored fields.
- **Git**: commit locally on `main`; no remote, no push.
